# Landfall — Path to 5/5

Companion to [`2026-09-07-production-readiness-review.md`](2026-09-07-production-readiness-review.md)
(current score ~1.8/5). This is what each rubric dimension looks like at **5/5**, the work
to get there, and — the part that separates 4 from 5 — **how you prove it**.

## The principle

> **4/5 is "built". 5/5 is "built + verified + evidenced."**

Shipping the nine P0 items from the audit gets Landfall to roughly 3.5–4. The last point
on every dimension is earned with a *verification artifact*: a back-test, a fault-injection
run, a signed review, a measured user trial. A number you can't independently check is a
3, however good the code is.

Two structural moves underpin almost every dimension:

1. **All quantitative work moves out of the LLM into deterministic tools.** The agent
   orchestrates and narrates; it never computes a cost, a wave, or an effort number in
   context. Enforced by tool design, prompt, an output guard that rejects un-sourced
   numbers, and the eval suite.
2. **Every run emits an evidence pack**, not just an answer: the inputs, the queries, the
   transformations, the assumptions applied, and the result — exportable as a calculation
   appendix that ships with the SoW.

## Dimension by dimension

### 1. Correctness — verified against an independent method, within a stated band

**5/5 looks like:** for any estate, Landfall's portfolio-level numbers (compute run-rate,
one-time migration cost, total effort) agree with **two independent methods** within a
declared tolerance, with every variance explained.

**Build**
- `estimate_compute_cost`, `plan_waves`, and the parametric effort model as deterministic
  tools (audit FIN-1..7, MA-1, PS-5).
- RAM-aware right-sizing; configurable, documented sizing model for the no-perf-data case
  (FIN-1, FIN-2).

**Proof — the back-test suite**
- 3+ reference estates of different shapes (small/greenfield, large/regulated, mixed
  PaaS). For each, produce the estimate **three ways**: (a) Landfall, (b) Azure pricing
  calculator + Azure Migrate business-case export for the same inventory, (c) a senior
  architect's spreadsheet model.
- Acceptance: portfolio totals within **±15%** across all three; line-item variances >10%
  each have a written cause. Re-run on every agent/tool change in CI.
- Publish the tolerance and the method in the output ("this estimate is modelled to ±15%
  at portfolio level pending discovery").

### 2. Defensibility — every number traces raw data → assumption → calculation, exportable

**5/5 looks like:** a pre-sales lead (or a client's reviewer) can click any figure in the
package and see the exact rows, the transformation, the assumptions applied, and the
confidence — offline, in the delivered document.

**Build**
- Structured deliverable with a stable ID on every figure (audit P0-5, PS-3).
- A **calculation appendix**: for each number — source tool, query/filter text, input row
  count, assumptions applied (linked to the assumptions register), formula, result,
  confidence.
- Machine-tracked assumptions & exclusions register (PS-4), not merged-by-hand prose.

**Proof**
- Review drill: hand the package to an architect who wasn't involved; they must be able
  to answer "where did this come from?" for 10 randomly chosen figures using only the
  delivered document. Pass = 10/10.

### 3. Completeness vs. mission — cost + landing zone + migration approach + plan + SoW inputs, all generated

**5/5 looks like:** the output package has all eight sections and **each is generated from
the client's data**, not filled from a template.

| Section | Generated by |
|---|---|
| Current-state analysis | `query_inventory` + data-quality report |
| Azure compute BoM + run-rate | `estimate_compute_cost` |
| One-time migration cost | cost tool (extras + migration module) |
| Landing-zone design | `design_landing_zone` / azure-enterprise-infra-planner |
| Disposition per app (6 R's + rationale) | disposition scorer (MA-2) |
| Wave plan with durations + critical path | `plan_waves` + duration model |
| Effort estimate + resource loading | parametric model on the client's counts |
| Assumptions / exclusions / risks register | tracked across the whole run |

**Build:** audit P0-1..6.

**Proof**
- Architect review board runs the package for a real (or realistic) engagement and signs
  that it needs **editing, not authoring** — every section is present and data-driven.
- Negative test: change the input estate (swap in a PaaS-heavy portfolio); every section
  changes accordingly.

### 4. Robustness to bad input — ingests real messy dumps, reports data quality, degrades gracefully

**5/5 looks like:** you can hand Landfall a genuine RVTools export or a ServiceNow CMDB
extract with all its real-world defects and get a valid estimate plus a data-quality
report that correctly names every defect.

**Build**
- The Normalize pipeline: file-type detection, configurable column mapping for RVTools +
  ≥2 CMDB shapes, unit normalisation, keyed upsert, ingest log (audit P0-1 / DE-1,2).
- `data_quality_report`: completeness scorecard, dupes, orphans, unit anomalies,
  "fields missing that the estimate needs" (DE-3).
- Graceful degradation: missing perf data → low-confidence path with a wider band, not a
  failure; missing dependencies → wave plan with a stated confidence caveat.

**Proof — the broken-dump corpus**
- 6+ deliberately damaged inputs: missing columns, wrong units (MiB vs GB, MHz), duplicate
  hosts, no dependency data, no perf data, mixed encodings / powered-off / template VMs.
- Acceptance: each produces (a) a valid estimate and (b) a data-quality report that flags
  **every** injected defect and nothing spurious. Plus a fuzz pass over column
  perturbations.

### 5. Usability for pre-sales — proposal-ready output, minimal per-deal tuning, usable by non-builders

**5/5 looks like:** a pre-sales consultant who has never seen the code produces a
SoW-ready package from a fresh client dump in under a day, with no engineer.

**Build**
- `estimation_config.json` implemented (audit P0-6) so per-deal tuning is a config edit,
  not a prompt edit.
- Structured export in a format that drops into the proposal template (P0-5).
- Self-service load: the operator uploads the raw dump; the pipeline does the mapping
  (removes the "adapt load_estate.py" step, OPS-5).

**Proof**
- Timed trial: 3 pre-sales people, 3 new estates, no engineer assistance. Acceptance: all
  produce a package an architect accepts, median time < 1 day, and they can each explain
  every section.

### 6. Understandability — a new consultant gets it in under an hour

**5/5 looks like:** given only the docs, a consultant new to Landfall can explain the
pipeline, run an estimate, and correctly interpret a Low-confidence answer within an hour.

**Build**
- Fix the docs to match what's built (the current SOP overstates: Normalize, config).
- One "how it actually works" page: the pipeline, the tools, the answer contract, the
  confidence model, the DRAFT boundary.
- Worked example end-to-end using `sample-estate/`.

**Proof**
- Comprehension test: 3 new people, 60 minutes with the docs, then a short task
  (run an estimate, interpret a confidence-Low line, find where a number came from).
  Pass = all 3 succeed unaided.

### 7. Operability — clean deploy, repeatable per engagement, known-good under pressure

**5/5 looks like:** `azd up` is green from a clean machine on Linux and Windows in CI;
per-engagement spin-up/teardown is a documented drill; the system degrades predictably
when a dependency is down.

**Build**
- Self-contained hooks (no `azd`-on-PATH dependency; SQL grant via Python not `sqlcmd`;
  Event Grid wiring reliable); retry-wrapped first SQL connect (audit OPS-1).
- `--tier prod` parameter set (SQL capacity up, Container App min-replica 1, Search Basic)
  for live engagements (OPS-3).
- Answer-quality observability: structured traces per tool call to App Insights + a
  dashboard + tool-error alerts (OPS-2).
- Export-before-teardown step (OPS-6).

**Proof**
- CI: clean-machine `azd up` → smoke estimate → `azd down --purge`, on both OSes, on every
  PR.
- Chaos drill: SQL paused, price API 503, Search index empty — each produces a clear
  degraded answer, never a wrong number or a stack trace to the user.
- Time-to-first-estimate for a new engagement measured and documented (< 30 min).

### 8. Security / compliance fit — signed-off data handling, isolation, least privilege, audit

**5/5 looks like:** a client CISO can read a data-handling statement and approve putting
their inventory in; engagements are provably isolated; every data access is logged.

**Build**
- One deployment per engagement; reliable fast `azd up/down` (audit SEC-2, P0-9).
- `query_inventory` auth **on by default**; private-endpoint parameter set (SEC-1, SEC-3).
- Client data kept out of logs (hash/template, not raw SQL) (SEC-5).
- Chat threads bound to the authenticated principal (SEC-6).
- `disableLocalAuth: true` on Foundry; keys off on Search (SEC-7); deps pinned (SEC-8).
- Published data-handling statement: residency (region-pinned), encryption, retention
  window, deletion procedure + evidence, sub-processor list (Foundry, AOAI, App Insights),
  what each retains (SEC-4).

**Proof**
- Pen test of `query_inventory` + the web UI by someone who didn't build it — passes with
  no high/critical.
- Isolation test: stand up two engagements, confirm no data path between them (DB, Search,
  storage, agent, logs).
- The data-handling statement reviewed and signed by a security officer (client or
  internal risk).
- Audit log demonstrably answers "who queried what, when" for a sample period.

### 9. Reliability of the agent — evaluated, grounded, deterministic where it matters, fails loud

**5/5 looks like:** the numeric output is 100% deterministic (tool-computed, byte-identical
on re-run); the text-to-SQL and grounding hit a published accuracy bar; the agent never
silently falls back — it says when it can't answer.

**Build**
- All math in tools; an **output guard** that rejects any agent message containing a
  numeric claim without a tool citation (audit AI-2).
- Allow-list SQL parse + statement timeout (AI-3).
- Batch consistency: one threaded pass or a pinned context snapshot so cross-question
  answers agree (AI-5).
- Explicit `store=True` if needed for chat memory (AI-6).

**Proof — the eval suite (CI gate on every agent version)**
- Text-to-SQL golden set (30+): **≥ 95%** exact-match on result.
- Full-estimate scenarios (8+): portfolio numbers within the declared band; **0**
  un-sourced numbers in the output; re-run produces identical figures.
- Fault injection: each tool made to fail in turn → the agent reports the failure, never
  invents. Pass = 100%.
- Grounding: retrieval recall on the golden doc-question set measured and tracked.
- Every `create_agent.py` change records its version + full eval scorecard; a regression
  fails the build.

## Deliverable polish — the artifact-generation bar

The three client-ready exports (PRD **E5.4**) and the studio deck (**E5.6**) are what a
client actually sees, so their production quality is a scored part of *Usability for
pre-sales* (dimension 5) and *Defensibility* (dimension 2). The bar is set by Anthropic's
own `docx` and `xlsx` document skills and the two PowerPoint skills the sponsor selected.

**Excel (`.xlsx`) — the standard from the `xlsx` skill**
(`github.com/anthropics/skills/tree/main/skills/xlsx`)
- **Formulas, never hardcoded results.** A derived cell holds `='Run rate'!B4*12`, not
  the number Python already computed. A reviewer must be able to change an input and see
  the model re-flow — that is the whole point of shipping Excel rather than a PDF table.
- Excel-2007-era functions only — `SUMIFS`, `INDEX`, `MATCH`, `IFERROR`. **Never**
  `XLOOKUP`, `XMATCH`, `SORT`, `FILTER`, `UNIQUE`, `SEQUENCE` (they fail or silently
  truncate in older Excel / LibreOffice). The six `_xlfn.`-prefixed functions only with
  the prefix.
- Formatting: Arial or Times New Roman; currency `$#,##0`; percentages as real fractions;
  negatives in parentheses; frozen header panes; column widths that fit the content.
- Every hardcoded input cell carries a comment naming its `F*` calculation-appendix id or
  external source.
- **Zero formula errors before delivery** — a headless LibreOffice recalc pass
  (`soffice --headless`, à la the skill's `recalc.py`) must come back clean. Green recalc
  proves the formulas *evaluate*; a human still checks they are *right*.

**Word (`.docx`) — the standard from the `docx` skill**
(`github.com/anthropics/skills/tree/main/skills/docx`)
- Page size **US Letter in DXA units** — do not ship the library's A4 default.
- Tables specify **both** column and cell widths; `ShadingType.CLEAR` for fills (never
  `SOLID`); lists via numbering definitions, not literal `•` glyphs; `PageBreak` only
  inside a paragraph.
- Authored so an architect's edits come back as Word **tracked changes** — every
  modification a proper `<w:ins>` / `<w:del>` with an `--author`; an `accept_changes`
  pass produces the clean proposal copy. This is how the DRAFT → owned-by-architect
  boundary (the core answer contract) shows up in the artifact itself.
- Read-back for QA via `pandoc -t markdown`.

**Narrative + structure — the Microsoft *Migration Execution Guide*
([`Azure/migration`](https://github.com/Azure/migration))**
- The deck, the Word doc and the dashboard follow the MEG lifecycle
  (*Assess → Plan/Design → Mobilise → Migrate → Optimise*) and its work-stream vocabulary
  (Digital Estate Discovery, Workload Mapping, Wave Planning, Project Plan, Risk Register,
  Migration-day Runbook) so the output reads like a Microsoft FastTrack deliverable.
- Deck story arc: executive summary (estate → run-rate → one-time → effort → plan shape)
  → methodology (the lifecycle as a chevron flow) → one section per stage → next steps.
- The `.xlsx` mirrors the MEG's sheet taxonomy where they overlap (estate, workload map,
  wave plan) so a customer already using the MEG can drop Landfall's output straight in.

**PowerPoint (`.pptx`) — the two sponsor-selected skills**
- **`presentation-skill`** (`github.com/siril9/presentation-skill`) — source-first:
  author an **`outline.json`** from the E5.1 package, never touch the `.pptx` directly;
  pick a style preset + composition grammar suited to an Azure migration business case;
  render via **pptxgenjs**; the **`qa_gate.py`** geometry/content/visual check must pass
  before the deck is delivered.
- **`ppt-master`** (`github.com/hugohe3/ppt-master`) — the design-rich path: SVG-layout →
  native DrawingML, firm `.pptx` template preserved, optional narration / speaker notes.
- Native editable objects only — shapes, tables, charts; never rasterised slides.
- Both need a Node toolchain (+ LibreOffice / Poppler for render checks) that the Azure
  Function runtime does not have, so E5.6 runs **side-car**: an architect runs the skill
  locally on the downloaded `latest.json`, or the dashboard invokes a dedicated build
  container. The Function's plain `python-pptx` deck (E5.4) stays the always-available
  fallback.

**Proof (Phase 2).** Three real estates → generate all four artifacts → (a) `xlsx`
LibreOffice recalc reports 0 errors and an independent hand-calc of three headline
figures ties out to the sheet; (b) `docx` opens clean in Word, tracked-changes round-trip
works, every figure resolves to an `F*` id; (c) the studio `.pptx` passes `qa_gate.py`
and the E7.4 un-sourced-number guard over its extracted text; (d) a pre-sales lead who
has not seen the code sends all four to a mock client with only light edits.

## Phasing

| Phase | Scope | Duration | Score after |
|---|---|---|---|
| **1 — Engine** | The 9 P0 items: ingestion + data-quality pipeline, deterministic cost engine, landing-zone output, wave engine, structured deliverable + traceability, `estimation_config`, eval harness, auth + data-handling doc, per-engagement isolation + reliable `azd up`. | ~10–12 wk, 1–2 eng | ~3.5–4 |
| **2 — Evidence** | Back-test suite (3 reference estates × 3 methods), broken-dump corpus, pen test, isolation test, timed usability + comprehension trials, chaos drills, CI on both OSes, architect review-board sign-off, CISO sign-off of the data-handling statement. | ~5–6 wk | **5** where the proof holds |
| **3 — Keep it 5** | Every agent version re-runs the full suite in CI. Quarterly re-benchmark against Azure price changes and new SKUs. Refresh reference estates yearly. Broken-dump corpus grows with every real messy dump seen. | ongoing | holds 5 |

**Total to 5/5: ~4 months with 1–2 engineers, plus review time from a senior architect and
a security officer in Phase 2.**

## The evidence pack (Phase 2 deliverable)

A single folder, versioned with the agent, that *is* the 5/5 claim:

- `backtest/` — 3 reference estates, the three independent estimates each, variance
  analysis, tolerance statement.
- `broken-dumps/` — the damaged-input corpus + expected data-quality reports.
- `evals/` — golden sets + latest scorecard + history.
- `pentest/` — report + remediation evidence.
- `trials/` — usability + comprehension trial results.
- `chaos/` — fault-injection run logs.
- `data-handling-statement.md` — signed.
- `SCORECARD.md` — the rubric, current score, link to each piece of evidence.

When someone asks "is it really production-ready?", you hand them `SCORECARD.md`.

## Residual risk (honest note)

- **Agent determinism** holds only as long as the output guard and eval suite are
  enforced; a prompt regression that lets the LLM do arithmetic drops dimension 9
  immediately. Treat the guard as load-bearing.
- **±15% correctness** is a modelling estimate, not a discovery-grade number. The output
  must keep saying so; a client who treats it as a fixed price is a commercial risk no
  amount of engineering removes.
- **Reference estates age.** Azure prices, SKUs, and CAF guidance move. Without Phase 3 the
  score decays.
