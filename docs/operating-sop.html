Landfall Operating Guide

How to turn a client's paper inventory into a defensible draft Azure landing-zone and migration estimate, using a Landfall instance someone has already deployed. Follow the phases in order — each one depends on the last.

Version 1.0 Updated 2026-09-07 Audience Migration architects & pre-sales consultants Prerequisite A deployed Landfall (see INSTALL.md)

Everything Landfall produces is a DRAFT for a human architect to review and own. Client inventory is typically incomplete and lacks performance data; every answer carries stated assumptions and a confidence level. It is a fast first pass, not a bid.

Phase 0Get access & approvals

One-time, per person. You need at minimum the chat URL and a sign-in. If you will also load data, you need a little more.

  1. Get the chat UI URL and a tenant account

    The person who deployed Landfall gives you SERVICE_WEB_URI and adds you to the Entra tenant. The UI is single-tenant — only accounts in that directory can sign in.

    opening the URL redirects you to a Microsoft sign-in, then to the chat page

  2. (Data loaders only) Get data-plane access

    Storage Blob Data Contributor on the storage account, a contained SQL user with db_datawriter, and az CLI + Python 3.11 locally. If you would rather not, ask the operator to run the load for you.

  3. Confirm the data-handling approval

    Before any client inventory is uploaded, confirm placing it in this storage account is covered by the MNDA / DPA — discovery questionnaire question SC7. Get the named sign-off.

    a written approval on file naming who signed and any redaction required

Phase 1Load the client estate

Landfall answers questions about data you have loaded. Two shapes of input, two stores: structured inventory → Azure SQL; narrative documents → the AI Search index.

  1. Collect the data pack

    Send the client discovery-questionnaire.html and collect §1: server/VM inventory (RVTools or vCenter export, or CMDB extract), application portfolio, dependency map, database inventory, storage & backup inventory, network diagrams, licensing position. MUST-tagged items block the estimate; chase those first.

  2. Capture the questionnaire answers

    Get every section answered — "unknown" is a valid answer, it tells you where to place an assumption. Save the answers as a document you will upload in step 4.

  3. Drop the inventory files in raw/inventory/

    Upload the client's exports — RVTools workbook, CMDB extract, application portfolio, dependency list — to the raw/inventory/ path of the storage account. Each file triggers the ingestion pipeline, which detects the format (RVTools vInfo, generic CMDB, or Landfall-native CSV), maps the columns to scripts/schema.sql, normalises units (MiB→GiB, OS strings), and loads Azure SQL. Re-uploading a corrected file replaces only its rows.

    az storage blob upload-batch --account-name <acct> --auth-mode login \
  -d raw/inventory -s ./client-inventory

    If a column is mis-detected, adjust the profile in src/api/ingest/core.py or (per engagement) supply overrides — see prd/tracker.md item E1.7.

    a <file>.dq.md data-quality report appears in answers/_ingest/; in chat, "how many servers are loaded?" returns the right count

  4. Read the data-quality report

    Open answers/_ingest/<file>.dq.md. It gives an overall confidence (High / Medium / Low) and a plain-English list of what is missing that the estimate needs — no performance data, unmapped servers, missing OS, orphan references. Send the client that list as the discovery follow-up.

  5. Upload the narrative documents

    Put architecture docs, the questionnaire answers, standards and runbooks (PDF / DOCX / MD) into the raw/docs/ path of the storage account. The indexer picks them up on a 6-hour schedule, or trigger it now.

    az storage blob upload-batch --account-name <acct> --auth-mode login \
  -d raw/docs -s ./client-docs
az rest --method post --resource https://search.azure.com \
  --url "<search-endpoint>/indexers/landfall-docs-ixr/run?api-version=2024-07-01"

    indexer status success; in chat, "search the documents for the migration driver" returns cited text

  6. Sanity-check the load

    Ask the agent to total vCPU / RAM and count servers past OS end-of-support, then eyeball it against what the client told you. If a count looks wrong, read the SQL the agent shows — a column mapping is usually the cause.

No client data yet? The repo ships sample-estate/ — 250 synthetic servers, 31 applications, and a completed questionnaire for a fictional retailer. Load it to learn the workflow, then clear it before real data goes in.

Phase 2Run an estimate in chat

Open SERVICE_WEB_URI, sign in, and work through the estimate one question at a time. Each browser tab keeps its own conversation thread — open a new tab to start clean.

  1. Establish the current state

    Ask for counts and totals: VMs by environment and OS, total vCPU / RAM / storage, EOL exposure, criticality spread. The agent uses query_inventory and shows the SQL it ran — keep that for the audit trail.

    e.g. "How many prod Windows Server 2012 R2 VMs, and total vCPU across them?"

  2. Size and cost the compute

    Ask for an Azure SKU recommendation and run-rate. The agent chains vm_rightsize then azure_retail_prices and must name the region, term and price date. Ask for both pay-as-you-go and 1-year / 3-year reserved.

    e.g. "Right-size the prod Linux fleet and give a monthly Azure compute run-rate in Sweden Central, PAYG and 1-year RI."

  3. Work the applications — disposition & waves

    Ask the agent to propose a disposition (the 6 R's) per application and group them into migration waves by dependency cluster. It reads dependencies and pulls constraints from search_documents.

  4. Scope the landing zone

    Ask what the landing zone must contain given the client's compliance scope and connectivity needs. The agent grounds this in microsoft_docs — Cloud Adoption Framework and the Azure landing zone reference architecture.

  5. Read the contract block on every answer

    Each answer ends with Answer · Basis · Assumptions · Data gaps · Confidence. Low / Medium confidence is a discovery gap to close, not a bug. Log every Assumption and Data gap as you go.

Phase 3Batch an RFP question sheet

When you have a long list of RFP clarification questions, let the batch runner answer them all instead of asking one by one.

  1. Prepare the workbook

    Put one question per row in a column headed Question in an .xlsx. Keep it to 300 rows or fewer — larger sheets are rejected.

  2. Drop it in the questions/ container

    Upload the workbook to the questions/ blob container. That is the trigger — nothing else to press.

    az storage blob upload --account-name <acct> --auth-mode login \
  -c questions -f rfp-questions.xlsx -n rfp-questions.xlsx

  3. Collect the answered workbook

    A few minutes later (for a few dozen rows), <name>_answered.xlsx appears in the answers/ container with columns Question · Answer · Sources · Status.

    rfp-questions_answered.xlsx in answers/

  4. Review the Status column

    Filter for error or empty. Re-ask those questions in chat — usually they need rephrasing or the underlying data isn't loaded.

Smoke test first. samples/smoke-questions.xlsx is a two-question sheet — run it once to confirm the pipeline works before uploading a real RFP.

Phase 4Assemble the draft estimate

Landfall gives you the raw material. You compose it into the estimate and put your firm's numbers on it.

  1. Pull the deliverable lines

    From the chat transcript and the answered sheet, gather: current-state summary, Azure compute bill of materials, landing-zone scope, 6 R's disposition, wave plan, run-rate cost (region + term + date stamped), migration effort range, and the risks & assumptions register.

  2. Apply your firm's rates

    Cross-check the effort against effort-and-resource-loading.html. The S / M / L / XL effort-hour bands, the RI term assumption, the non-prod & DR uplift %, and the PM / testing / cutover overhead % are yours — set them in an estimation_config.json the agent reads, so it applies your rates rather than inventing them.

  3. Consolidate assumptions & gaps

    Merge every "Assumptions" and "Data gaps" line into one register. Map it to the questionnaire's working-assumptions register (§16, AS-01…) and risk register (§17, RK-01…) so the RFP risk section writes itself.

  4. Architect review — then watermark

    A named architect reviews and owns the numbers. Every exported page carries "DRAFT — architect review required" and the confidence column is non-optional. Never let the numbers go into a proposal as a fixed price.

Phase 5Close out the engagement

  1. Export and archive

    Download the answered sheets from answers/ and save the chat transcript with the estimate. That is the evidence pack for the review.

  2. Park or tear down

    Between engagements the idle cost is a few dollars a month. To take it to zero, the operator runs azd down --purge; azd up rebuilds in ~15 minutes next time.

  3. Delete client data if required

    If the contract requires it, remove the storage account and purge the Key Vault and Foundry account so no client inventory persists. Confirm deletion in writing.

RefThe agent's tools

You don't call these — the agent picks them. Knowing which one answered helps you judge the answer.

ToolWhat it doesAnswers like
query_inventoryTurns a plain-English question into one read-only SQL SELECT over the four tables, runs it, returns rows and the SQL."how many…", "total vCPU", "apps with no owner"
vm_rightsizeMaps each server to an Azure VM SKU + disk tier with a stated heuristic — sizes to peak with headroom, or one size down and flagged low-confidence when there's no utilisation data."what SKU for this server", "right-size the fleet"
azure_retail_pricesLive pay-as-you-go and reserved prices from the public Azure Retail Prices API, cached."monthly cost", "1-year vs 3-year RI"
search_documentsHybrid search over the narrative docs in raw/docs/. Surfaces client constraints — compliance, network, DR, maintenance windows."what does the client say about…"
microsoft_docsMicrosoft Learn — Cloud Adoption Framework, Azure landing zone reference, target-service sizing."what should the landing zone contain"

RefThe answer contract

Every substantive answer ends with these five labelled lines. If one is missing, ask the agent to complete it before you use the number.

LineWhat to check
AnswerThe number or recommendation itself.
BasisWhich tool / query / document produced it. A cost line must name region, term and price date.
AssumptionsWhat the agent had to assume. Each one goes in your register.
Data gapsWhat was missing. This is where you place a discovery activity.
ConfidenceHigh / Medium / Low. Low is not a defect — it means the inventory was thin here.

RefDo & don't

Do

  • Load and sanity-check data before asking estimate questions.
  • Keep the SQL the agent shows — it's your audit trail.
  • Ask one thing at a time; build the estimate incrementally.
  • Log every Assumption and Data gap as you go.
  • Run the smoke sheet before a real batch.
  • Put a human architect's name on the final numbers.

Don't

  • Treat any output as a bid or a fixed price.
  • Upload client data before the SC7 approval is on file.
  • Trust a cost figure with no region / term / date.
  • Assume a low-confidence answer is wrong — close the gap instead.
  • Exceed 300 rows in a batch question sheet.
  • Leave a client's data in the storage account after close-out if the contract says otherwise.

RefTroubleshooting

SymptomCause / fix
Chat returns 503 — AGENT_ID not setThe deploy's post-provision step didn't finish. Ask the operator to re-run it (azd hooks run postprovision).
query_inventory answers 0 or errorsData isn't loaded, or the Free SQL database auto-paused after an hour idle — the first query wakes it (~30–60 s); retry once.
A count looks wrongRead the SQL the agent shows. Almost always a column-mapping mismatch in Phase 1 step 3 — reload with the corrected mapping.
Document search returns nothingDocs aren't in raw/docs/, or the indexer hasn't run since you uploaded. Trigger it (Phase 1 step 4) and wait for success.
Batch sheet never produces an answered fileThe Event Grid subscription on questions/ is missing. Operator: azd hooks run postdeploy.
First request after a quiet period is slow (~10 s)Expected — the chat app scales to zero and the SQL database auto-pauses. It warms up on the first request.
Cost figure seems highCheck whether Azure Hybrid Benefit and reservations were applied, and whether the agent right-sized per server or just scaled a total. Ask it to redo with those explicit.

AppxFor the operator

You maintain the Landfall instance other people use. This is the short list; the detail is in the repo.

  • Deploy / redeploy — INSTALL.md (clean machine) or DEPLOY.md (tooling in place). azd up provisions, runs post-provision (SQL schema, search index, agent), deploys both services, then post-deploy wires the Event Grid subscription.
  • Lock down the chat UI — required. Container App → Authentication → Microsoft (single-tenant) so only your directory can sign in. CLI recipe in DEPLOY.md.
  • Harden query_inventory — recommended. It ships as an anonymous HTTP function; put Entra auth in front of it with scripts/funcapp-auth.json and re-attach the tool with AGENT_TOOL_AUTH=managed python scripts/create_agent.py.
  • Change the agent's prompt or tools — edit scripts/create_agent.py and re-run it. It publishes a new agent version; the chat UI and batch runner reference the agent by name and pick it up with no redeploy.
  • Add the client's OpenAPI / SQL connection — if create_agent.py warns it found no search connection, add it in the Foundry portal (Management center → Connected resources) and re-run.
  • Costs — idle a few dollars a month; ~$5–15/month at 5–20 estimate runs. azd down --purge between engagements.
