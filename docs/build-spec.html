Project Sounding

A low-code Azure agent that reads a client's on-premises server and application inventory from Data Lake and drafts the landing-zone and migration numbers you need for an RFP proposal — no discovery tools installed on the client estate.

Prepared 2026-09-07/ Owner upendra25312@gmail.com/ Budget < $30 / month/ Usage 5–20 runs / month, bursty/ Input client inventory, ≤ 5 GB

What this is for

You are responding to an RFP to build an Azure landing zone and migrate a client's servers and applications. The client will not run Azure Migrate or install any agent or appliance on their estate. Instead they export what they have — RVTools dumps, CMDB extracts, an application portfolio spreadsheet, a questionnaire, some architecture docs — and drop it in your Data Lake.

Sounding turns that pile into answers you can put in the proposal: how many VMs and of what size in Azure, what the landing zone must contain, how the apps group into migration waves, which disposition (the 6 R's) fits each app, and a rough order-of-magnitude cost for both the Azure run-rate and the migration effort.

Read this to every stakeholder. Sounding produces a draft estimate for a human architect to review and own. Client-supplied inventory is typically incomplete, stale, and inconsistent; performance data is usually missing. Every number the agent gives carries stated assumptions and a confidence level. It is a fast first pass, not a bid.

The SQL model

Free Azure SQL database. Load the client files into these tables; keep a schema.sql the text-to-SQL tool can read. Nullable everywhere — client data has gaps.

-- servers: one row per discovered VM / physical host
server_id · hostname · env (prod/nonprod/dr) · os_name · os_version · os_eol_date
vcpu · ram_gb · provisioned_disk_gb · used_disk_gb
cpu_avg_pct · cpu_peak_pct · ram_avg_pct        -- often NULL; drives right-sizing confidence
cluster · datacenter · powerstate · app_id (FK) · notes

-- applications: one row per business application
app_id · app_name · business_owner · criticality (1-4) · users
tech_stack · db_engine · internet_facing (bit) · compliance_scope
disposition -- filled by the agent: Rehost/Replatform/Refactor/Repurchase/Retire/Retain
complexity -- filled by the agent: S/M/L/XL · wave -- filled by the agent

-- dependencies: directed edges between apps or servers
src_id · dst_id · port · protocol · direction · confidence

-- storage: volumes / shares / databases needing a target
storage_id · server_id (FK) · type (block/file/object/db) · size_gb · iops · target_service

Agent runtime. The Migration Estimator is a Microsoft Foundry prompt agent — versioned, addressed by name (landfall-migration-estimator), not an asst_ id. Both front ends call it through the Responses API (responses.create(…, agent_reference)): the chat UI threads context with previous_response_id; the batch runner is stateless per question. Re-running create_agent.py publishes a new version and the front ends pick it up with no redeploy.
Event Grid, not polling. Both blob triggers (normalize on raw/inventory/, batch runner on questions/) run on the Functions Flex Consumption plan, which requires an Event Grid source. An Event Grid system topic sits on the storage account; the questions/ subscription is created by a post-deploy hook because its webhook needs the function's blobs_extension key, which exists only after first deploy.

Agent tools

01

query_inventory — Azure SQL

OpenAPI tool over a small Function: POST /query {question} → gpt-4o writes a read-only SELECT constrained to the schema above → runs it against the Free SQL database → returns rows and the SQL used. Answers “how many prod Windows Server 2012 VMs”, “total provisioned vCPU”, “apps with no owner”.

02

vm_rightsize — Function with documented heuristic

Input: rows of {vcpu, ram_gb, cpu_peak_pct, used_disk_gb}. Output: a recommended Azure SKU per server (Dsv5 / Esv5 / Fsv2 family), plus disk tier. Heuristic, stated in the response: if utilisation data is present, target 75% headroom on peak; if absent, assume the allocation is oversized and map to the next SKU down, flagged low-confidence. Never silently guesses.

03

azure_retail_prices — Azure Retail Prices API

OpenAPI tool over the public, no-auth endpoint https://prices.azure.com/api/retail/prices. The agent pulls live pay-as-you-go and 1yr/3yr reserved prices for the SKUs from tool 02, in the client's target region. Real numbers in the estimate, not memorised ones.

04

search_documents — Azure AI Search (Free)

Hybrid search over the narrative docs index, top-k 12. Surfaces client constraints: compliance scope, network topology, maintenance windows, DR requirements, things that change the landing-zone design.

05

microsoft_docs — Microsoft Learn MCP

Hosted MCP server https://learn.microsoft.com/api/mcp (streamable HTTP, public, read-only) added as an MCP tool, require_approval: never. Grounds landing-zone and migration guidance in current Microsoft docs — Cloud Adoption Framework, Azure landing zone reference architecture, VM SKU families, Azure SQL / AKS target sizing.

System prompt (core): “You help a migration architect estimate an Azure landing zone and server/app migration from client-supplied inventory. Use query_inventory for any count or sizing question and show the SQL. Use vm_rightsize then azure_retail_prices for cost. Use microsoft_docs for landing-zone and target-service guidance. Use search_documents for client constraints. Every estimate must end with: Assumptions, Data gaps, Confidence (High/Medium/Low). Never state a cost without naming the region, term, and price date. If inventory is missing a field needed for an answer, say so and give a ranged estimate.”

Estimation methodology the agent follows

Deliverable lineHow the agent derives it
Current-state summaryAggregates from servers/applications: counts, vCPU/RAM/storage totals, OS mix, EOL exposure, criticality spread
Azure compute BoMvm_rightsize per server → SKU counts; adds ~10–20% for non-prod/DR per client RPO/RTO in docs
Landing-zone scopeCAF Azure landing zone accelerator baseline (mgmt groups, hub-spoke, firewall, Bastion, Log Analytics, policy) tuned by compliance scope + connectivity needs from search_documents and microsoft_docs
6 R's dispositionPer app: EOL OS or clear PaaS fit → Replatform/Repurchase; low criticality + idle → Retire candidate; else Rehost. Writes disposition back to SQL
Wave planGroups apps by dependency clusters (keep tightly-coupled apps in one wave), then orders by criticality asc and complexity asc; writes wave
Run-rate costazure_retail_prices: compute (PAYG + 1/3yr RI), managed disk, bandwidth egress estimate, landing-zone fixed services; monthly + annual, region + date stamped
Migration effortT-shirt hours per app by complexity (S/M/L/XL bands you set), × count, + landing-zone build + testing + cutover + PM overhead %; expressed as a range
Risks & assumptions registerCollected from every tool call where data was missing or low-confidence
You own the bands. The S/M/L/XL effort-hour bands, the RI term assumption, the non-prod uplift %, and the PM overhead % are your firm's numbers — put them in a estimation_config.json the agent reads as a tool or system-prompt block, so the model applies your rates, not invented ones.

Bursty usage works in your favour. At 5–20 estimate runs a month, every compute tier here sits idle most of the time and bills near zero: Container Apps and Functions scale to zero, Azure SQL Free auto-pauses after 1 hour, and gpt-4o only bills while a run is active — a full estimate pass (20–40 agent turns) costs a few tens of cents. Expect real months to land around $5–15, most of which is the Azure OpenAI tokens for the runs you actually do.
Between engagements, park it. Nothing here needs to run continuously. When no estimate is in flight you can: leave it as-is (idle cost is already ~$0), or fully stop spend by deleting the resource group and redeploying from an infra-as-code template (Bicep) plus a SQL schema.sql next time — a 10-minute redeploy. Keep the ADLS account and Key Vault if you want to retain past clients' data; delete them too if contracts require it.

Build phases

01

Storage, budget alert, SQL

ADLS Gen2 (--hns-enabled true), folders raw/inventory/, raw/docs/, questions/, answers/. Cost Management budget $25 with alerts. Create the Azure SQL Free offer database; run the DDL for the four tables; store schema.sql in the repo.

out: storage + empty inventory schema + budget alert

02

Models

Foundry: deploy gpt-4o and text-embedding-3-small (both GlobalStandard), ~30K TPM cap each.

out: two capped model endpoints

03

Normalize function

Durable Function, Event Grid blob trigger on raw/inventory/ (source=BlobSource.EVENT_GRID — Flex Consumption): detect file type (RVTools vs CMDB vs app portfolio by header signature), map columns to the schema, upsert into SQL. Log unmapped columns to answers/_ingest_log.txt so you can see what was dropped.

out: client files → populated SQL tables, with a gap log

04

Docs index

Portal “Import and vectorize data” on raw/docs/. Built-in cracking, 2000/500 chunks, embeddings at dimensions = 512, 6-hourly schedule.

out: hybrid index of client narrative docs

05

Tool functions

Deploy three HTTP Functions with OpenAPI specs: query_inventory, vm_rightsize, azure_retail_prices (a thin proxy that adds $filter and caches). Read-only SQL login for query_inventory. Put estimation_config.json in an app setting or blob the functions read.

out: three callable tool endpoints

06

Agent

Foundry prompt agent, gpt-4o, system prompt from above, created / versioned by scripts/create_agent.py (PromptAgentDefinition + agents.create_version). Attach all five tools (three OpenAPI, one AI Search, one MCP → learn.microsoft.com/api/mcp). Test with 20 real estimate questions via the Responses API; verify tool routing and that every answer carries assumptions + confidence.

out: working Migration Estimator agent, addressed by name

07

Chat UI — Container Apps

Containerize a minimal chat app, deploy to Container Apps, min replicas 0. Enable built-in Entra ID auth. App calls the agent via Managed Identity.

out: internal chat URL behind org login

08

RFP question sheet — Durable Functions

Fan-out / fan-in orchestration (code below). Output columns: Question · Answer · Basis · Assumptions · Confidence · Sources. 300-row guard. Email the workbook via Microsoft Graph from the final activity.

out: upload RFP questions.xlsx → answered workbook by email

09

Evaluate & calibrate

Build a golden set from a past migration you know the real answer to. Score groundedness, tool-call accuracy, and numeric closeness. Tune the heuristic in vm_rightsize and the bands in estimation_config.json until the draft lands within your acceptable margin.

out: calibrated agent + documented margin of error

RFP question sheet — Durable Functions

Python v2 model. Fan-out / fan-in: parse the sheet, answer each question as a throttled parallel activity, write a structured workbook. host.json: maxConcurrentActivityFunctions: 3.

# function_app.py — azure-functions, azure-functions-durable, azure-identity,
#   azure-ai-projects (2.6), azure-storage-blob, pandas, openpyxl
import io, os, logging
import pandas as pd
import azure.functions as func
import azure.durable_functions as df
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.storage.blob import BlobServiceClient

app  = df.DFApp()
cred = DefaultAzureCredential()
_c   = {}  # clients built lazily — keep worker function-indexing fast

def _blob():    return _c.setdefault("b", BlobServiceClient(os.environ["STORAGE_URL"], credential=cred))
def _openai():  return _c.setdefault("o",
    AIProjectClient(endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"], credential=cred).get_openai_client())

AGENT_NAME = os.environ.get("AGENT_ID", "")  # Foundry prompt agent, addressed by name
MAX_ROWS   = 300
FMT = "\n\nReturn: Answer, Basis, Assumptions, Confidence, Sources."

# Flex Consumption: blob triggers must be driven by Event Grid
@app.blob_trigger(arg_name="src", path="questions/{name}.xlsx", connection="STORAGE_CONN",
                  source=func.BlobSource.EVENT_GRID)
@app.durable_client_input(client_name="client")
async def start(src: func.InputStream, client):
    name = os.path.basename(src.name)
    _blob().get_blob_client("work", name).upload_blob(src.read(), overwrite=True)
    await client.start_new("orchestrator", client_input=name)

@app.orchestration_trigger(context_name="context")
def orchestrator(context: df.DurableOrchestrationContext):
    name = context.get_input()
    qs   = yield context.call_activity("parse_sheet", name)
    if qs == "TOO_MANY_ROWS": return
    rows = yield context.task_all([context.call_activity("ask", q) for q in qs])
    yield context.call_activity("write_results", {"name": name, "rows": rows})

@app.activity_trigger(input_name="name")
def parse_sheet(name):
    data = _blob().get_blob_client("work", name).download_blob().readall()
    d = pd.read_excel(io.BytesIO(data))
    if len(d) > MAX_ROWS: return "TOO_MANY_ROWS"
    return d["Question"].fillna("").tolist()

@app.activity_trigger(input_name="q")
def ask(q):
    try:
        resp = _openai().responses.create(input=q + FMT,
            extra_body={"agent_reference": {"type": "agent_reference", "name": AGENT_NAME}})
        text = (resp.output_text or "").strip()
        if not text:
            return {"q": q, "answer": "", "cites": "", "status": f"run_{resp.status}"}
        return {"q": q, "answer": text, "cites": _citations(resp), "status": "ok"}
    except Exception as e:
        logging.exception("ask failed")
        return {"q": q, "answer": "", "cites": "", "status": f"error: {e}"}

def _citations(resp):  # walk resp.output[*].content[*].annotations for filename/title/url
    seen = []
    for item in getattr(resp, "output", None) or []:
        for content in getattr(item, "content", None) or []:
            for a in getattr(content, "annotations", None) or []:
                lbl = getattr(a, "filename", None) or getattr(a, "title", None) or getattr(a, "url", None)
                if lbl and lbl not in seen: seen.append(lbl)
    return "; ".join(sorted(seen))

@app.activity_trigger(input_name="p")
def write_results(p):
    out = pd.DataFrame([{"Question": r["q"], "Answer": r.get("answer", ""),
                         "Sources": r.get("cites", ""), "Status": r["status"]} for r in p["rows"]])
    buf = io.BytesIO(); out.to_excel(buf, index=False); buf.seek(0)
    nm = p["name"].replace(".xlsx", "_answered.xlsx")
    _blob().get_blob_client("answers", nm).upload_blob(buf, overwrite=True)
    logging.info("wrote answers/%s", nm)
Post-deploy wiring. The questions/ → start Event Grid subscription is created by scripts/eventgrid.{ps1,sh} (an azd postdeploy hook), because its webhook URL carries the function's blobs_extension system key, which only exists once azd deploy has published the function. Idempotent; re-run with azd hooks run postdeploy.

The name

Recommendation first.

Soundingrecommended

To take a sounding is to drop a weighted line and measure the depth you cannot see — exactly what you are doing with a client estate you cannot instrument. Short, no Azure collision; resources as sounding-agent, sounding-sql, sounding-fn, sounding-aca.

Fathomalternative

A unit of depth, and the verb for finally understanding something complex. Fits an assessment tool well; very short.

Landfallalternative

The moment a voyage reaches shore — leans into the “landing zone” framing. More outcome than method.
