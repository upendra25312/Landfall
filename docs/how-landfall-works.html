1 What Landfall is — and is not

A low-code Azure agent that turns a client's paper inventory into a defensible draft landing-zone and migration estimate, with no discovery tooling on the client estate.

Landfall is a Microsoft Foundry prompt agent that orchestrates a set of deterministic Python tools. You give it a client's server and application inventory (CSV / Excel / RVTools / a CMDB export); it right-sizes each server to an Azure VM, prices the estate at live retail rates, designs a Cloud Adoption Framework landing zone, scores each application against the 6 Rs, orders the migration into waves, and assembles the whole thing into an Excel / Word / PowerPoint package plus a Pricing-Calculator proof of estimate.

Landfall is not a discovery product (it never touches the client network), not an authoritative quote (it is explicitly a DRAFT), and not an LLM doing arithmetic — every number is computed by a tool, and an output guard fails the run if an un-sourced figure ever reaches the deliverable. The agent decides which tool to call and how to narrate the result; it does not invent the result.

The one-sentence model. The agent orchestrates; the Python tools compute; export.py authors the documents. If you remember only that, the rest of this page follows.

2 The pipeline: five stages

Every engagement moves left to right. Each stage writes into the engagement's private folder so the next stage — and any later question — reads the same ground truth.

1 · LoadUpload the raw inventory to the engagement. Files land in raw/engagements/<customer>/<project>/ and nowhere else.
2 · Ingest & DQEach file is detected, column-mapped, normalised and loaded into SQL. A data-quality report names every gap, dupe and orphan and sets a confidence hint.
3 · ModelRight-size → price compute, storage, run-rate extras → design the landing zone → score dispositions → plan waves → size effort.
4 · AssembleAll tool output is folded into one structured package: eight proposal sections, every figure carrying an F‑id, a calculation appendix, an assumptions register.
5 · PublishThe package is rendered to .xlsx / .docx / .pptx and the dashboard; the real Azure Pricing Calculator is driven for the POE. Prior versions are snapshotted.

Stages 1–2 are the ingestion pipeline (event-driven: dropping a file triggers it). Stages 3–5 are the estimate, driven by the agent when you ask for it or click a prompt card. You can re-run stages 3–5 as often as you like — the inventory in SQL is the fixed input, so a re-run with the same data produces byte-identical figures.

Tenancy — why the folder path matters

One Landfall deployment serves many engagements. Isolation is the <customer>/<project> key: it scopes the blob folders, and SQL Row-Level Security keys every one of the six inventory tables on engagement_id and fails closed — a query with no engagement context returns zero rows. A tool call without an engagement is a 400. You never type the key; you pick or create the engagement and it rides with every request.

3 The twelve tools

The agent's whole toolbox. Each is a deterministic HTTP function over the deployed API — same input, same output, no model in the maths.

ToolStageWhat it returns
query_inventoryanyAnswers a natural-language question about the estate as SQL over the six tables (200-row cap, single SELECT, 20 s timeout). This is the "how many prod Windows servers?" path.
vm_rightsizeModelPer server: the Azure VM SKU that covers both its vCPU and its RAM at p95 utilisation, with a low / expected / high band and the binding dimension named.
estimate_compute_costModelThe compute bill of materials — PAYG vs 1-yr / 3-yr reserved, Azure Hybrid Benefit on or off, per environment, at a stated region + price date.
estimate_storage_costModelFile, database and object storage priced from the storage table to the right Azure service (per-VM disk stays in the compute BoM).
estimate_run_rate_extrasModelBackup, monitoring, egress, support — plus one-time migration cost (tooling, dual-run, replication egress).
design_landing_zoneModelA CAF landing zone from the portfolio + compliance scope: management groups, subscriptions, hub-spoke networking, an IP plan, a policy overlay, DR pairing, and a conformance score against the Azure ALZ / AI-LZ checklists.
score_dispositionsModelA 6 R disposition (rehost / replatform / refactor / …) per application, with the rationale.
plan_wavesModelThe dependency graph → move groups → risk-ordered waves, plus a dated schedule and the critical path.
assemble_estimateAssembleFolds every tool result into one package — the eight sections, the figure list, the calculation appendix, the assumptions / exclusions / data-gaps register.
export_estimatePublishRenders a package to .xlsx / .docx / .pptx (deterministic Python in export.py).
publish_estimatePublishWrites the package + the three exports to the engagement's estimate/ folder, snapshots the previous version, and can kick the Pricing-Calculator POE.
azure_retail_pricesModelThe live Azure Retail Prices API — the only external call Landfall makes, and it is anonymous and read-only.

Two more tools support the workflow rather than the maths: run_engagement (bulk-ingest a whole folder) and build_landing_zone_diagram (emit the target diagram as .drawio / .svg / .png).

4 The answer contract

Whatever Landfall tells you — in chat, in the deck, in the workbook — comes with the same three things attached. Learn to look for them.

  1. An F‑id. Every headline number in the deliverable has a figure id (F12, F27…). The calculation appendix has one row per F‑id: the formula, the input values, the assumptions applied, the confidence. You can trace any number to its arithmetic without leaving the document.
  2. A basis. A one-line statement of where the number came from — "250 servers × p95 vCPU, bound on RAM for 38 of them; Standard_D-series; sweden central retail, 2026-09-08". If a figure has no basis, the output guard fails the build; it never ships.
  3. A confidence level — High Medium Low — set by the data-quality report, not guessed. See the next section for exactly what drives it.

A cost answer additionally carries a low / expected / high band and its top three drivers (the inputs the total is most sensitive to). A range that looks wide is telling you the truth about the input data — narrow it by filling the data gap the register names, not by asking Landfall to be more precise.

Reading a number, in practice. Get the total from the dashboard or the chat → find its F‑id → open the calculation appendix (a sheet in the workbook) → read the formula + inputs + assumptions → check the confidence and the band. If any step doesn't resolve, that is a bug — report it.

5 The confidence model

Confidence is a property of the input data, assigned by the data-quality report at ingest and carried through every downstream figure. It is deterministic — the same dump always gets the same rating.

LevelWhat it meansTypical triggers
High The estate is well described and carries real utilisation history. Right-sizing is bound on measured p95, not on provisioned specs. ≥ 80 % of servers have ≥ 14 days of CPU + memory samples; vCPU / RAM present on nearly every row; few orphan dependencies.
Medium The inventory is complete enough to size on, but performance data is thin, so right-sizing leans on provisioned specs and a safety margin. Some performance coverage but below the High bar; a minority of rows missing a non-critical field; a mapping override was applied.
Low A structural gap makes the number a rough order of magnitude. Say so explicitly to the client. > 50 % of servers have no utilisation history; vCPU or RAM missing / unparseable on > 30 % of rows; a required file was rejected and the estate is loaded with a named gap.

The report also lists data gaps — the specific missing inputs that would raise confidence if supplied. Those flow into the assumptions register as "client-ask" items and into the agent's "what's missing?" answer. A Low-confidence line is not a failure of Landfall; it is Landfall refusing to imply precision the data can't support.

Cost figures are capped at Low by design. Any pre-discovery run-rate or one-time cost number is reported at most Low even when the inventory itself is well described — without measured utilisation and confirmed commercial terms it is a planning range, not a quote. Inventory facts (counts, vCPU totals, EOS servers) still carry their data-driven rating. So a package's overall confidence is usually Low; that is the honest default, not a red flag.
Never a silent partial load. If a file is unrecognised it is rejected with a reason; if it is damaged it is either rejected or loaded with the gap named in the report. Landfall never quietly drops half a file and prices the rest as if it were whole.

6 The DRAFT boundary

Landfall gets you to a reviewable first pass fast. These decisions stay with the architect — the tool marks them, it does not make them.

Landfall decides (deterministically)

  • The VM SKU that covers each server's p95 vCPU and RAM
  • Retail / reserved / hybrid pricing arithmetic at a stated date
  • The CAF landing-zone topology implied by the portfolio + compliance scope
  • A first-cut 6 R disposition and a risk-ordered wave plan
  • Which data gaps exist and how they cap confidence

The architect owns

  • Whether each disposition is right for this client's strategy
  • Commercial terms — actual discounts, EA / MCA specifics, the margin
  • Any figure marked Low before it goes to the client
  • Application-level refactor / retire calls that need business context
  • Signing off the package as fit to send

Practically: the Word document opens ready for tracked changes, every figure resolves to an F‑id, and the assumptions register is the list of things you should confirm or correct with the client. Editing the package is the expected workflow — authoring it from scratch is not.

7 Worked example: the sample estate

The repository ships a synthetic estate under sample-estate/ — deterministic, seeded, and the basis for every eval. Here is the whole pipeline over it. Your numbers will match to the dollar if you run it yourself.

  1. Load the inventory

    Five files: servers.csv, applications.csv, dependencies.csv, storage.csv, performance.csv. In a real engagement you drag them onto the engagement's upload panel; for the sample they load via sample-estate/load_estate.py.

    250 servers, 31 applications, 484 dependency rows, 566 storage volumes, 5,190 performance samples in SQL

  2. Read the data-quality report

    The sample estate is well described — every server row carries p95 CPU and RAM, plus a 5,190-row performance time series. Inventory facts rate Medium. The overall package confidence is still Low, because cost figures are capped at Low pre-discovery (previous section) and the register flags six applications whose disposition needs a business decision.

    inventory facts Medium · run-rate cost Low · overall Low · 6 open disposition decisions in the register

  3. Right-size and price

    vm_rightsize maps 250 servers (1,940 current vCPU) to Azure SKUs bound on p95 vCPU and RAM. estimate_compute_cost, estimate_storage_cost and estimate_run_rate_extras price the result at swedencentral retail on the config's price date (the eval config assumes 80 % 1-yr reserved and Azure Hybrid Benefit on Windows — every such choice is a numbered row in the assumptions register).

    compute + disk $81,439/mo · storage $16,184/mo · extras $16,287/mo

  4. Design the landing zone, score dispositions, plan waves

    design_landing_zone derives the hub-spoke topology, a regulated spoke for the PCI-scoped apps, and DR pairing. score_dispositions gives each of the 31 apps a 6 R call; plan_waves orders them into risk-first waves with a dated schedule.

    a CAF topology, 31 dispositions, a multi-wave plan with a critical path

  5. Assemble and publish

    assemble_estimate folds it all into one package — eight sections, every figure an F‑id, the calculation appendix, the assumptions register. publish_estimate renders the workbook, document and deck and populates the dashboard.

    total Azure run-rate $113,911/mo ($1,366,927/yr) · one-time migration $73,218 · effort 834 person-days · services $650,286

  6. Trace a number

    Take the $113,911/mo total. It is compute_monthly + storage_monthly + extras_monthly. Each of those has its own F‑id and appendix row — compute_monthly resolves to the per-server SKU list × hours × the swedencentral retail rate on the stated date. No step is opaque.

    every headline figure resolves to tool-computed arithmetic in the calculation appendix

Run it yourself. python evals/runner.py executes this exact chain (with deterministic synthetic price books) as scenario SC1 and asserts the headline figures land in band. Scenarios SC2–SC8 vary the levers — production-only, 3-year reserved, dev/test pricing, no AHB, Low confidence, a 10-server slice.
