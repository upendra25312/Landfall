# evals/ — Landfall evaluation harness (PRD E7)

Offline. No Azure, no live model. Run it:

```bash
.venv2/Scripts/python evals/runner.py          # scorecard + writes SCORECARD.md
.venv2/Scripts/python evals/runner.py --quiet  # scorecard only
```

Exit code 0 iff the golden-SQL exact-match rate ≥ 95% **and** every full-estimate
scenario passes **and** every fault-injection case passes. `tests/test_evals.py`
wraps the same functions so `pytest` catches regressions, and
`.github/workflows/evals.yml` runs the whole thing on every push / PR (a stale
`SCORECARD.md` fails the build).

## E7.1 — golden text-to-SQL (`golden_sql.json`)

32 `question → T-SQL → expected result` cases over the sample estate. The runner:

1. checks each `sql` passes `tools._safe_select` (the read-only SELECT guard),
2. executes it against an in-memory SQLite copy of `sample-estate/*.csv`
   (`sample_db.py`, with a small test-only T-SQL→SQLite shim), and
3. asserts an exact match against `expected` (as of 2026-09-08).

The complementary gate — *a live model generates SQL that matches the golden SQL* —
needs credentials and runs in CI, not here.

## E7.2 — full-estimate scenarios (`scenarios.json`)

8 scenarios. Each runs the whole tool chain (`pipeline.py`, deterministic synthetic
price books from `fixtures.py`) and `assemble_estimate`, then checks:

- every headline figure lands inside its expected band (~±8% of the committed baseline),
- every figure is traceable (has a calculation-appendix formula),
- a re-run is byte-identical.

Scenarios cover: full estate, prod-only, 3-year RI, dev/test pricing, aggressive
disposition, low data-quality confidence, no AHB, and a 10-server slice.

## E7.3 — fault injection (`faults.py`)

Sends a broken request (empty body, wrong types, missing required fields) to every
deterministic HTTP tool and asserts it returns a clean error (HTTP ≥ 400, a body
whose only content is an `error` string) — never a 200 with fabricated numbers.
Also checks that `assemble_estimate` omits a section (and records the gap) when an
upstream tool's slot carries `{"error": ...}`.

## E7.4 — output guard (`output_guard.py`)

`check_message(text, sourced_values)` flags any numeric claim (money, %, counts
with a unit, magnitudes ≥ 1000) that isn't backed by a tool-sourced value or a
citation (a figure id, a tool name, an assumption/basis line). The harness runs it
against each scenario's own `summary_markdown` — the assembled deliverable must
carry zero un-sourced numbers by construction. `check_message` is importable for a
real agent-output check too.

## Files

| File | Purpose |
|---|---|
| `runner.py` | the harness — `run_golden`, `run_scenarios`, `run_faults`, `scorecard`, `main` |
| `golden_sql.json` | the 32 golden query cases |
| `scenarios.json` | the 8 scenario definitions + expected bands |
| `sample_db.py` | sample CSVs → in-memory SQLite + T-SQL→SQLite shim |
| `pipeline.py` | run every tool deterministically → assembled package |
| `fixtures.py` | synthetic price / rate books (no network) |
| `faults.py` | fault-injection cases (E7.3) |
| `output_guard.py` | the un-sourced-number checker (E7.4) — also importable |
| `SCORECARD.md` | last run's result (regenerated by `runner.py`; CI fails if stale) |

When the sample estate or a tool's maths changes on purpose, re-run the runner and
commit the updated `SCORECARD.md` and any adjusted `expected` values.
